Late Entry in Looped Language Models

What if a new token could skip the early reasoning passes?

Looped language models deepen reasoning by repeatedly running every token through the same layers, turning recurrence depth directly into slow sequential decoding. Our finding is that a new token can skip early passes and read deeply processed context instead. Late Entry uses this asymmetry to accelerate generation, while Wake verification checks predictions in the background to restore full-depth output when needed.

01 · The Scientific Insight

One Late Pass Outperforms Two Early Passes

Standard early exit runs the first K passes and stops, leaving cached past tokens at shallow depth. When we instead keep past context at full depth T and run only the final passes on the new token (after lightweight interface alignment), fewer late passes beat more early passes across architectures.

Why Deep Context Substitutes for Local Passes

In multi-step reasoning, earlier tokens have already iterated through all T passes. Reading their final-pass representations lets a new token jump straight to late refinement instead of rebuilding features from Pass 1.

02 · Progressive Walkthrough

From Late Entry to Background Wake Verification

Late Entry speeds up generation, but raises two immediate questions: how do past tokens acquire deep KV caches if every token skips early passes, and what happens on the rare 6% of tokens where a fast guess slips? Step through the three chapters below.

What is Wake verification?

A token is generated tentatively using only the final passes, then checked once its full-depth 1 → T computation catches up in the background over subsequent steps.

04 · Architectural & Depth Generalization

Deeper Recurrence Makes Late Entry Faster and More Stable

Testing the exact same Huginn-3.5B checkpoint across test-time recurrence depths T ∈ {8, 16, 32, 64} (36 to 260 effective layers) reveals a striking scaling law: while full-depth block decoding hits a flat ~3.3× ceiling, Late Entry + Wake accelerates up to 8.42× exact (and 10.57× lossy) as deeper loops stabilize late representations.

Huginn-3.5B Across T = 8 → 64 (GSM8K, n = 1,319)

Full-depth block saturates near 3.3×; Exact Wake (K = T/4) climbs to 8.42×

• Exact Wake K=T/4 (τ=0) ┄ Exact Wake K=T/2 ■ Lossy K=T/4 (τ=∞) ─ Full K=T block

Two Families, One Principle

Purely looped (Ouro) and Prelude-Core-Coda (Huginn) architectures

Unlike Ouro-1.4B / 2.6B, which loops all layers uniformly (T = 4), Huginn-3.5B wraps a 4-layer recurrent Core between a non-recurrent 2-layer Prelude and 2-layer Coda. Late Entry runs the Prelude once, skips directly to the final K Core steps, and refreshes Coda KV states in the final catch-up step.

Zero Extra Layer Calls & Same-GEMM Wake

At single-request decode, GPU forward passes are bound by streaming model weights from HBM rather than arithmetic compute (on H100, the Ouro-2.6B Tensor-Core ridge point is 348 query rows/pass).

Packing the (1+B)2 = 81 active candidate-block rows together with ≤18 background wake catch-up rows totals ≤99 rows ≪ 348 ridge rows, so completing exact 1 → T KV caches adds zero extra serial forward calls and negligible latency. Finished wake states then share the existing single lm_head output GEMM inside one static CUDA graph.

Proposition 1 (Exactness & Termination): Verified across 258/258 adversarial fp64 tests; every rollback commits exact token y*i* at index i*+1 > u, guaranteeing strict finite-step termination. Replacing trained mask proposals with a parameter-free 4/3/2-gram suffix drafter still yields 1.37×–2.25× multiplicative Wake speedups.

H100 Roofline & Multi-Request Serving (C ∈ [1, 32])

Zero-shot Lp roofline law calibrated strictly on K = 4 (8.3% MAPE; 11/12 optimal B*(C) match)

Skipping early passes on rejected draft branches cuts per-step row-passes by 39%, sustaining 2.31× decode throughput (1.67× online serving with prefills) at C=32 via adaptive B ∈ {8,4,2}.
